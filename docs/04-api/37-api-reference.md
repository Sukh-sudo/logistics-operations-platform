# 1. Overview

The Logistics Operations Platform exposes a REST API.

All requests and responses use JSON.

Every endpoint follows the same conventions.

---

# 2. API Principles

The API is:

- RESTful
- Stateless
- Versioned through `/api/v1`, with unversioned compatibility routes
- Predictable
- Consistent

Business logic belongs in services.

Controllers expose business capabilities.

# 5. Response Standards

Successful response

```json
{
  "success": true,
  "data": {},
  "timestamp": "2026-06-24T15:30:00Z",
  "requestId": "4cbd615e-6ea8-4e97-ad10-e353c6e56d64"
}
```

Error response

```json
{
  "success": false,
  "error": {
    "code": "PACKAGE_NOT_FOUND",
    "message": "Package not found."
  },
  "timestamp": "2026-06-24T15:30:00Z",
  "path": "/package-events/CON1234567",
  "requestId": "4cbd615e-6ea8-4e97-ad10-e353c6e56d64"
}
```

Successful domain values are always under `data`. Validation errors additionally
include an `error.details` string array. HTTP `204` responses have no body.

# 7. Pagination

```
GET /trips?page=1&pageSize=50
```

Response

```json
{
  "success": true,
  "data": [],
  "pagination": {
    "page":1,
    "pageSize":50,
    "total":1200,
    "totalPages":24
  },
  "timestamp": "2026-06-24T15:30:00Z"
}
```

Pagination is opt-in for endpoints returning arrays. `page` defaults to `1`
and `pageSize` defaults to `50` when another collection control is supplied.
The maximum `pageSize` is `200`. Without collection controls, existing list
routes continue to return the complete array under `data`.

---

# 8. Filtering

Examples

```
GET /trips?status=IN_PROGRESS

GET /fleet/trucks?status=AVAILABLE

GET /dashboard/packages?packageStatus=DELIVERED
```

General list filtering performs a case-insensitive exact match on fields
present in the returned representation. Module-specific filters such as
dashboard date/terminal filters and notification recipient filters are applied
by their services before the response boundary.

---

# 9. Sorting

Examples

```
GET /trips?sort=plannedDeparture

GET /terminals?sort=terminalCode

GET /shipments?sort=-createdAt
```

Prefix the returned field with `-` for descending order. Nested returned fields
may use dot notation.

## Terminals

```

```

Terminal `name` is generated by the service and is not accepted in create or update requests. Names use the terminal city and its three-digit per-city sequence, beginning at `000`:

```json
{
  "city": "Calgary",
  "name": "Calgary-000"
}
```

## Fleet

```
POST /fleet/trucks

GET /fleet/trucks

GET /fleet/trucks/{id}

POST /fleet/drivers

GET /fleet/drivers

GET /fleet/drivers/{id}

POST /fleet/assignments

GET /fleet/assignments

POST /fleet/assignments/{id}/release

GET /fleet/availability?terminalId={terminalId}
```

Truck creation generates `unitNumber`; clients provide the operating purpose
and owning terminal:

```json
{
  "purpose": "LAST_MILE",
  "terminalId": 1,
  "licensePlate": "ABC-123",
  "year": 2026,
  "make": "Ford",
  "model": "Transit"
}
```

The format is `LM|MM` + the owning Terminal's three-letter `terminalCode` + a
five-digit sequence, such as `LMCAL00001` or `MMEDM00001`.

New assignments require `tripId`, `truckId`, `trailerId`, and `driverId`.

## Customer Tracking

```
GET /tracking/{shipmentNumber}
```

Returns shipment progress, package statuses, terminals, and customer-visible
milestones from the Shipment Snapshot and immutable Shipment Events. Internal
ids and notification recipient data are not returned.

## Notifications

```
GET /notifications?recipient={email}

GET /notifications/{id}

PATCH /notifications/{id}/read

POST /notifications/{id}/resend
```

The current delivery channel is in-app. Reads and resend requests append
Notification Events and update Notification Snapshots transactionally.

## Reporting

```
GET /reports/deliveries
```

Optional filters are `fromDate`, `toDate`, `originTerminalId`, and
`destinationTerminalId`. Date filters use inclusive UTC calendar dates and
apply to shipment creation time.

## Users

```
POST /users

GET /users

PATCH /users/{id}
```

`PATCH /users/{id}` accepts `email`, `firstName`, and/or `lastName`. Employee
numbers remain immutable. The update writes `USER_UPDATED` and the
`UserSnapshot` in one Prisma transaction.

---

## Dashboard

```
GET /dashboard/summary

GET /dashboard/recent-events

GET /dashboard/packages

GET /dashboard/containers

GET /dashboard/trailers
```

`GET /dashboard/summary` and `GET /dashboard/recent-events` accept these optional query parameters:

| Parameter | Format | Meaning |
|-----------|--------|---------|
| `fromDate` | `YYYY-MM-DD` | Inclusive UTC start date |
| `toDate` | `YYYY-MM-DD` | Inclusive UTC end date |
| `terminalId` | Positive integer | Current asset terminal |
| `packageStatus` | Package status enum | Current package status |
| `trailerStatus` | Trailer status enum | Current trailer status |

Example:

```http
GET /dashboard/summary?fromDate=2026-07-01&toDate=2026-07-22&terminalId=1&packageStatus=IN_TRAILER&trailerStatus=IN_TRANSIT
```

# 11. Handheld workflow API

The mobile contract uses `/api/mobile/v1` and requires JWT authentication
except for the initial online login and token refresh.

```text
POST /api/mobile/v1/auth/login
POST /api/mobile/v1/auth/refresh
POST /api/mobile/v1/auth/logout
GET  /api/mobile/v1/bootstrap

POST /api/mobile/v1/work-sessions
POST /api/mobile/v1/work-sessions/{id}/pause
POST /api/mobile/v1/work-sessions/{id}/resume
POST /api/mobile/v1/work-sessions/{id}/complete
GET  /api/mobile/v1/work-sessions/active

POST /api/mobile/v1/scans
POST /api/mobile/v1/sync
GET  /api/mobile/v1/sync/status
POST /api/mobile/v1/events/{eventId}/reverse

GET /api/mobile/v1/packages/{trackingNumber}
GET /api/mobile/v1/containers/{containerBarcode}
GET /api/mobile/v1/trailers/{trailerId}
GET /api/mobile/v1/routes/{routeCode}
```

Every scan uses a unique `clientEventId`. Parsed synchronization batches
return one durable result per command with `ACCEPTED`, `REJECTED`,
`DUPLICATE_ACCEPTED`, or `REVERSED`.

The browser client in `apps/handheld-simulator` consumes this contract through
a same-origin Vite development proxy. It persists commands before transmission
and submits only the documented scan DTO fields; local outbox metadata is
never sent to the API.

Supervisor reads extend the existing dashboard API:

```text
GET /dashboard/terminal-kpis/handheld
GET /dashboard/terminal-kpis/handheld/employees
GET /dashboard/terminal-kpis/handheld/exceptions
GET /dashboard/terminal-kpis/handheld/unloaded-containers
```

# 13. Design Principles

Every endpoint should:

- Validate input
- Authenticate
- Authorize
- Execute business logic
- Return consistent responses

No endpoint should bypass business services.
